## 1. 解决的是"功能不可用"而不是"功能不完整"

阶段 3.4 报告里第 6 条限制写得很直白：

> 用户开了夜间模式，翻页就没了。

这不是"少了个小功能"，而是**这个功能没法日常使用**。所以这一阶段
优先做它，而不是继续加新模块。

## 2. 为什么不能直接复用 `allowlist`

看起来是同一类数据（一组域名 + 上限 + 去重 + 脏数据清洗），但语义相反：

| 文件 | 语义 |
| --- | --- |
| `filters/allowlist.js` | **不要**在这个站点上做事（暂停过滤） |
| `site-memory.js` | **要**在这个站点上做事（自动开启夜间模式） |

混在一起会让两个功能的开关互相串：用户在 A 站暂停广告过滤，
A 站的夜间模式也会被自动打开。

所以这里**复用规则、不复用存储**：

- 复用：`normalizeEntry`（域名规范化，含拒绝 URL）
- 复用：标签边界匹配（`www.example.com` 命中 `example.com`，`notexample.com` 不命中）
- 独立：存储键（`darkSites` / `readerSites`）、上限（100 vs 200）

### 2.1 为什么上限是 100 而不是 200

`allowlist` 里可能积累大量"临时暂停"的站点，200 合适；
而"我常用的站点"是个更小的集合，100 足够，且能让一次读取的字符串更短。

### 2.2 为什么按模块分键

```js
configKeyFor('dark')   // → 'darkSites'
configKeyFor('reader') // → 'readerSites'
configKeyFor('adblock') // → 抛错
```

最后一个抛错是刻意的：**新增按站点记忆的模块必须显式登记**，
否则会出现"用了不存在的配置键"这种静默失败。

## 3. 真实环境抓到的高危缺陷

### 缺陷（高）：注入函数自己返回的失败被当成成功

| 项 | 内容 |
| --- | --- |
| **位置** | `lib/inject.js` 的 `runInFrame` |
| **现象** | 注入函数返回 `{ok:false, error:'NO_CONTENT'}`，上层却认为成功，把这个站点写进了"已开启"名单 |
| **后果** | 用户看到"开关自己跳"：点开启失败，但存储里记成已开启，下次加载自动尝试、又失败 |
| **根因** | `executeScript` 成功 + 函数跑完 = 从浏览器角度看**完全成功**。`runInFrame` 只检查了 `result === undefined`，没检查 `result.ok === false` |
| **修复** | 显式区分三层失败（见下） |
| **测试** | `inject-dark.test.js` 三条：函数返回 ok:false、无 error 字段、空结果 |

### 3.1 三层失败必须分开

| 层 | 来源 | 错误码 |
| --- | --- | --- |
| 注入本身失败 | `executeScript` 抛错 | `HOST_PERMISSION_DENIED` / `INJECT_FAILED` |
| 结果为空 | `results` 空数组 | `NO_RESULT` |
| **注入函数业务失败** | 返回 `{ok:false, error}` | 函数自己的 error |

第三层是最容易漏的，因为它**看起来完全成功**。这一层不区分，
造成的后果就是"写入了一份错误的持久状态"。

这个缺陷是 `site-memory` 的测试抓到的——
`测试「注入失败时不写名单」` 直接断言了 `darkSites` 应为空。
如果只测"名单能写对"，永远不会发现它。

## 4. 设计上的三个细节

### 4.1 生成名单只在注入成功后

```js
if (!out.ok) return out;             // ← 先返回
if (ctx.config.get('remember')) {    // ← 才写名单
  ...
}
```

顺序反了就是上面那个缺陷。

### 4.2 `remember:false` 时只影响当前页面

用户可能只是想临时眯一下眼，不想让这个站点永久变暗。所以有一个开关。

### 4.3 `host` 参数优先，非法时退回 tab 推断

```js
const host = hostOf(msg.host) || (await hostOfTab(deps, tabId));
```

popup 通常已知 host（它从 `tab.url` 拿的），直接传更快；
但传了非法值（比如整个 URL）不该直接失败——退回从 tab 推断即可。

`hostOf` 明确拒绝带 `/` 或 `:` 的输入：
`https://x.test/a` 在朴素的字符串处理里会被截成 `https`，那是一条永远匹配不上的记录。

## 9. 已知限制（如实）

| # | 项 | 说明 |
| --- | --- | --- |
| 1 | **页面加载时还没自动应用** | `dark.should-apply` 接口已就绪，但**内容脚本还没调用它**。也就是说：名单记住了，但打开页面仍需手动点一下 |
| 2 | 阅读模式还没接入 | `site-memory` 已支持 `reader`，但阅读模式的行为与夜间模式不同（阅读模式改变了 DOM 结构，自动应用要在 DOM 就绪后做） |
| 3 | 未做设置页的"已记忆站点"列表 | 接口 `dark.sites` 已就绪，UI 未做 |
| 4 | 名单上限 100 且无提示 | 超限静默丢最旧 |
| 5 | 不区分路径 | `example.com/a` 与 `example.com/b` 共享开关。这是刻意的（按域名而非按页面） |

### 关于第 1 条

这是本阶段**明确未完成**的部分，不能算作"已实现"。

要让"打开页面自动应用"生效，需要：

1. 内容脚本在 `document_idle` 时向 SW 发 `dark.should-apply`
2. SW 回复后，内容脚本自己套样式

但这里有一个架构选择要慎重：**内容脚本直接操作 DOM** 意味着
`dark.js` 的注入函数要复制到内容脚本里（MV3 内容脚本不支持 ES module）。
两份实现的分叉风险与阅读模式那次相同。

更干净的做法是：内容脚本只负责**发起请求**，SW 用 `executeScript` 应用样式。
代价是页面加载时会多一次消息往返 + 一次注入。

这个决定留到下一阶段，因为两种方案都有真实的取舍，不该顺手选一个。
