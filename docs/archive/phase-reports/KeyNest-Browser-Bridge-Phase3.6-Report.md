## 1. 为什么这一轮做这个目标

阶段 3.5 报告里明确留了一个架构空白：

> 「打开页面自动应用」还没做：`dark.should-apply` 接口已就绪，
> 但内容脚本还没调用它。这需要先决定内容脚本与注入函数的关系
> （两份实现的分叉风险 vs 多一次往返），两种方案都有真实取舍。

选它作为本轮目标，是因为它**正好适合"不影响用户用电脑"这个约束**：

- 全部是纯代码与单元测试，不需要启动浏览器
- 架构决策本身不需要运行时验证就能想清楚
- 真实验收可以之后补，而架构错了之后返工代价大

---

## 2. 架构决策：内容脚本只发起，不自己注入

这是阶段 3.5 留给本阶段的核心问题。两条路：

| 方案 | 代价 |
| --- | --- |
| **A. 内容脚本自己套样式** | MV3 内容脚本不支持 ES module → `darkToggle` 必须复制一份 → 两份实现分叉（阅读模式已经吃过这个苦） |
| **B. 内容脚本只发请求，SW 用 `executeScript` 注入** | 多一次消息往返（几毫秒）+ 一次注入 |

**选了 B。** 理由是收益不对称：

- 分叉风险是**长期**的：两份实现会随迭代慢慢偏离，而偏离的表现是
  "单元测试全绿、真实浏览器行为不对"——正是 3.3 那一类最难查的缺陷
- 多一次往返是**一次性**的几毫秒，且只发生在页面加载时

所以注入函数在整个项目里**始终只有一份**。

### 2.1 时序：为什么等 `load` 而不是 `DOMContentLoaded`

内容脚本跑在 `document_idle`，那时 DOM 已稳定。但页面自己的首屏脚本
可能在这之后还在改样式（很多 SPA 会）。

所以自动应用延后到 `window.load` 之后再 `setTimeout(..., 0)`：
给页面自己的脚本一点时间，避免我们的滤镜被它覆盖。

这不保证一定赢（有些脚本更晚），但比立刻应用好。

---

## 3. 最关键的一条：自动应用绝不请求权限

页面加载时**没有用户手势**。此时 `permissions.request` 的两种结果都很糟：

| 结果 | 用户感受 |
| --- | --- |
| 被静默拒绝 | 功能不生效，没有任何提示 |
| 弹出确认框 | **莫名其妙**——用户只是打开一个网页，浏览器却问"是否允许访问此站点" |

第二种更糟：用户会怀疑浏览器或扩展出了问题。

所以给注入层加了 `requestPermission: false` 模式：**只查不请**。

```js
const granted = requestPermission
  ? await ensureHostPermission(deps.permissions, origin)  // 查，没有就请求
  : await hasHostPermission(deps.permissions, origin);   // 只查
```

已授权 → 注入；未授权 → 安静地什么都不做。

用户想用这个功能，得先在 popup 里主动点一次（那一次有手势，能弹框）。

### 3.1 这个缺陷是被测试抓出来的

写 `auto-apply.test.js` 时，第一条用例就挂了：

```
FAIL-SAFE: 未授权时安静返回 HOST_PERMISSION_DENIED（不请求、不注入）
  expected request to be 0, actual 1
```

原因是 `injectInto` 当时的实现里根本没有 `requestPermission` 这个选项——
我在文档注释里写了它，但代码没改（前一次 `str.replace` 没命中目标文本）。

**这正是"测试断言了不该发生的事"的价值**。如果只测"自动应用能生效"，
这个缺陷会一路带到真实浏览器，表现为"每次打开网页都弹授权框"。

## 4. 新增：离线自检脚本

`browser-extension/scripts/selfcheck.mjs`，`npm run selfcheck`。

### 4.1 它解决什么问题

真实 Chrome 验收代价高（启动浏览器、注册 Host、注入键鼠），
而且会占用用户机器。但**装配层的问题不需要真实浏览器就能查出来**：

```
  PASS  核心模块已注册 — vault,registry,adblock,reader,dark
  PASS  manifest 与模块声明的权限一致
  PASS  每个 handler 的消息类型都显式声明了来源
  PASS  门禁表里没有指向不存在 handler 的条目
  PASS  门禁表没有重复键（重复会静默覆盖）
  PASS  模块声明的能力都在 CAPABILITIES 里
  PASS  内容脚本没有 import（MV3 硬约束）
  PASS  内容脚本发出的消息类型都在门禁表里
  PASS  options_ui 页面在特权白名单里
  PASS  至少有一个模块支持自动应用 — reader,dark
  PASS  没有声明高风险权限
  PASS  manifest 与 package.json 版本一致
=== 结果：14/14 通过 ===
```

### 4.2 它立刻抓到了两个问题

**问题 1**：`dark.should-apply` 与 `dark.sites` 两个消息类型**没有在门禁表里声明**。

未声明的类型会落到默认 `any`——任何来源都能发。这不是立刻的安全漏洞
（这两个消息本身无害），但它破坏了"门禁表是攻击面清单"这个性质：
看一眼清单会以为只有这些入口，实际上还有暗的。

**问题 2**（自查发现）：我在修问题 1 时手滑插入了重复的 `reader.toggle`/`reader.query`。

对象字面量里的重复键**静默覆盖**，没有任何报错。所以加了一条扫源码的检查：

```js
const keys = [...block.matchAll(/^\s*'([a-z][a-z0-9.-]*)':/gm)].map((m) => m[1]);
const dups = [...new Set(keys.filter((k, i) => keys.indexOf(k) !== i))];
```

运行时不依赖（运行时已经看不到被覆盖的那个），直接读源码。故意造一个重复验证过它确实会红。

### 4.3 它**不能**替代真实验收

这一点必须写清楚。离线自检用的是假 `chrome.*`，它无法发现：

| 类别 | 例子 |
| --- | --- |
| Chrome 的字段名/常量 | 阶段 2.9 的 `thirdParty` vs `domainType` |
| 权限的运行时时序 | 阶段 3.3 的"`permissions.getAll()` 看起来已授权但 `executeScript` 拒绝" |
| 真实 DOM 行为 | 阶段 3.3 的提取算法在真实页面上的表现 |
| dNR 规则合法性 | Chrome 会拒绝整批规则，假 dNR 不会 |

所以它是**补充**，不是替代。

## 5. 实现要点

### 5.1 `autoApply` 协议

模块只需实现两个方法：

```js
autoApply: {
  shouldApply(host, ctx) -> boolean,   // 该不该在这个站点自动开
  apply(tabId, ctx) -> Promise,        // 打开它（内部走 injectInto）
}
```

宿主（`lib/auto-apply.js`）统一扫一遍已注册模块，逐层过滤：

1. 没实现 `autoApply` → 跳过
2. 模块被禁用 → 跳过（用户关掉的功能不该在加载时又冒出来）
3. `shouldApply` 返回 false → 跳过（不产生任何副作用）
4. `apply` 抛错 → **记录并继续**（一个模块坏了不能拖垮另一个）

第 4 条有测试守着：「单个模块抛错不拖垮其他模块」。

### 5.2 `tabId` 只来自 `sender.tab.id`

```js
const tabId = sender && sender.tab ? sender.tab.id : null;
```

**不接受消息体里的 `tabId`**。否则网页可以声称自己是别的标签页，
从而触发对别人的注入。

同时拒绝非主 frame（`sender.frameId !== 0`）：iframe 里的页面
不该被同一个动作改两次。

### 5.3 阅读模式也接入了按站点记忆

阶段 3.5 只做了夜间模式。这一轮补上阅读模式：

- 新增 `readerSites` / `remember` 配置
- `reader.toggle` 成功后写名单（**失败不写**，与夜间模式同一条规则）
- `autoApply.shouldApply` 查名单

阅读模式的自动应用会**安静失败**：如果这个站点在名单里但当前页不是文章，
`NO_CONTENT` 不会产生任何 UI——不该在每次打开非文章页时都留个错。

## 10. 已知限制（如实）

| # | 项 | 说明 |
| --- | --- | --- |
| 1 | **未经真实浏览器验证** | 见 §7 |
| 2 | 自动应用只在页面加载时跑一次 | SPA 路由变化（`pushState`）不会重新触发。需要在内容脚本里监听 `popstate`/`hashchange`，但要处理"用户手动关掉后又路由变化"的语义 |
| 3 | 阅读模式自动应用可能"抢"用户的关闭 | 用户在某站点手动退出阅读模式，刷新后又被自动打开（因为名单里还有）。这是设计选择，但没有"临时退出"的概念 |
| 4 | 无 UI 显示"本站已自动应用" | 用户可能不知道某站点的夜间模式是从名单来的 |
| 5 | 名单上限 100 且无提示 | 超限静默丢最旧 |
| 6 | 离线自检的假 chrome 很宽松 | 它不校验 Chrome 的字段名与权限时序（见 §4.3） |

### 关于第 3 条

这是最需要想清楚的一条。当前行为：用户在 `a.com` 开了夜间模式 → 刷新 →
自动开。用户在 `a.com` 手动关掉 → 名单被移除 → 刷新 → 不会自动开。**这是对的。**

但如果用户只是临时眯一下眼（点关闭），名单就被清掉了，
下次再开还要手动点。所以有个 `remember` 配置，但 UI 上还没有"只关这一次"的选项。
