# AI API Key 类型设计

## 为什么做成一个「类型」而不是「一个功能」

KeyNest 的类型系统本来就是可扩展的（`TypeDef` = 标签 + 字段模板）。
信用卡带「卡号/有效期/安全码」，身份带「证件号/地址/电话」——
API Key 只是**又一组字段**，没有理由为它写专门的 UI 或存储。

做成类型的好处：
- 复用现有的搜索、筛选、收藏、回收站、导入导出、字段打码
- 用户还能自己改字段（比如某些服务需要 endpoint 或组织 ID）
- 不需要动 `vault.dat` 的格式（`types` 本来就是数据的一部分）

## 字段设计

| 字段 | 打码 | 理由 |
| --- | --- | --- |
| 服务商 | 否 | OpenAI / Anthropic / Google / 自建…用来筛选和搜索 |
| API Key | **是** | 核心秘密。打码显示，复制仍可用 |
| Base URL | 否 | 自建/代理端点，配合某些客户端时需要 |
| 组织 / 项目 | 否 | OpenAI 的 org id、Anthropic 的 workspace |
| 额度 / 计费 | 否 | 记「$20/月」这类信息，避免反复去后台查 |
| 到期时间 | 否 | 有的 key 有有效期，过期了要换 |

为什么把 Key 放在**自定义字段**而不是复用 `password` 字段：

- `password` 在列表行里有「点右侧钥匙图标复制」的快捷操作，
  那是为登录场景设计的；API Key 更常见的动作是整体复制。
- 更重要的：`password` 参与「弱密码」「重复使用」这两个安全统计。
  一个 50 位的十六进制 API Key 会被算成「强」，但它根本不该进那个统计；
  而如果同一个 key 用在两个服务里（少见但可能），也不该报「重复使用」。

所以 API Key 用 `secret: true` 的自定义字段，语义更准。

## 迁移：老库怎么看到这个类型

类型表存在 `vault.dat` 里。加了新内置类型后，**已有的库不会自动出现它**——
需要在打开时补进去。

位置在 `VaultData::migrate_legacy()`：那里已经在做「条目用到但类型表没有的补进去」。
再加一条：内置类型缺失时补上（只补**缺失的**，用户删掉的不强行加回来）。

这一点很重要：如果用户主动删了「笔记」类型，我们不该每次打开都加回去。
所以只补 `DEFAULT_TYPES` 里出现、且当前类型表完全没有的——
但这样就无法区分「用户删了」和「老库没有」。

取舍：**只补 API Key 这一个**，且只在它从未出现过时补。
其余内置类型维持现状（不动）。
